# 同频现场 · 演示脚本

目标：**在 4 分钟内走完主链路**，并让评委随时看到 Agent 的工具轨迹、证据与三种边界状态。

## 演示前准备（约 1 分钟）

```bash
# 终端 1：前端（必需）
cd frontend
npm install          # 首次
npm run dev          # http://127.0.0.1:5173

# 终端 2：后端（可选，接上后能看到真实后端工具轨迹）
cd backend
python -m venv .venv
.venv\Scripts\activate
pip install -r requirements-dev.txt
python -m uvicorn app.main:app --reload --port 8010   # 8000 可能被 Windows 保留
```

用后端时，在 `frontend/.env.local` 写 `VITE_API_BASE_URL=http://127.0.0.1:8010` 并重启前端。
打开演示控制台底部会显示当前数据源：**「本地后端 Agent」** 或 **「前端本地镜像」**——两者都能完整演示。

浏览器：`F12` → 设备模拟（iPhone 14 Pro / 390×844）。桌面直接访问也可以。

## 主路径（约 90 秒，必须完整走完）

| 步骤 | 操作 | 讲解要点 |
| --- | --- | --- |
| 1 | 打开 `http://127.0.0.1:5173` | 默认入口就是**模拟 QQ 音乐演出详情页**：海报、歌手、时间、地点、票价、本场曲目、同行安全提示 |
| 2 | 指出顶部「QQ音乐 · 概念功能 Demo · 非官方页面」与页面上的 API 限制说明 | 明确这是概念功能，**不复制 QQ 音乐界面**，只借鉴品牌绿 |
| 3 | 点 **「AI 找同频搭子」** | 进入**音乐数据授权页**：收藏歌曲 / 常听歌手 / 近期播放 / 关注演出 / 歌单标签，逐项可勾 |
| 4 | 点「全部授权」→「授权并继续」 | 强调**最小必要授权**，右侧实时给出脱敏预览 |
| 5 | 在输入框用一句话说需求（或点示例话术） | 示例：「我第一次看星野回声，最喜欢《夜航的信》，想找人一起排队候场、副歌一起唱，3 个人以内，只在公开场合见面。」 |
| 6 | 点「让 Agent 理解我的需求」 | 进入**意图确认页**：活动 / 歌曲 / 目的 / 风格 / 人数 / 性别 / 见面 / 年龄段 / 安全，逐项可改 |
| 7 | 点「确认无误，让 Agent 开始匹配」 | 进入 **Agent 执行进度页**，六个阶段依次点亮 |
| 8 | 在进度页停留 2 秒 | 用户模式只显示自然语言进度；**评委模式才会显示工具名与耗时**（下一步演示） |
| 9 | 点「查看匹配结果与证据」 | 3 位候选人：匹配度、共同歌曲、共同目的、差异点、**可核对的理由** |
| 10 | 点某位候选人卡片上的 **「查看依据」** | 抽屉里给出：工具调用步骤、使用的数据来源、被排除的人与规则、每项得分、理由引用的具体歌曲/歌手/目的、**等待确认的下一步** |
| 11 | 关闭抽屉，点「邀请 ta 同行」 | 双向确认：`邀请已发出 → 对方已查看 → 双方确认` |
| 12 | 等出现「进入同频临时房间」并点击 | 强调：**只有双方都确认，Agent 才会调用 create_room**（后端未确认会返回 409） |
| 13 | 在房间页从上往下讲 | 双向确认状态、**公开集合点**、**音乐破冰问题**、候场任务、退出与举报 |
| 14 | 点「演出结束了，生成现场回忆卡」 | 共同歌曲、现场关键词、同一场的成员、一句现场回忆 |

## 演示控制台（左下角「演示」竖标签）

打开后可以现场切换，所有切换都会写入 `sessionStorage`，**刷新不丢**：

| 分组 | 选项 | 用途 |
| --- | --- | --- |
| 评委演示模式 | 开 / 关 | 开启后显示工具名、输入输出摘要、耗时、fallback 状态 |
| 演示案例 | 案例 1 正常匹配成功 | 完整跑完八个工具 |
| | 案例 2 安全条件过滤后无匹配 | 严格安全条件把同场候选人全部排除，返回 `no_match` 并逐条列出规则原因 |
| | 案例 3 大模型不可用走本地 fallback | 跳过模型调用，用规则解析与文案模板完成匹配 |
| 页面状态 | 正常 / 载入较慢 / 网络异常 | 演示加载态与错误态（含重试入口） |
| | 重置演示数据并回到首页 | 清空会话，回到默认状态 |

## 六个加分点

1. **Agent 真的在调工具**：标准流水线 8 次工具调用（`parse_social_intent` → … → `generate_grounded_reason`），
   后端模式下轨迹来自后端；评委模式可逐条查看。
2. **理由可核验**：每条理由都能在「查看依据」里找到对应的歌曲、歌手或目的；引用校验不过会退化为短句，绝不编造。
3. **安全是硬条件**：同场 / 年龄段 / 性别 / 人数 / 见面意愿 / 拉黑举报六条确定性规则，被排除的人会给出规则原因。
4. **不编造候选人**：案例 2 展示「宁可 no_match，也不凑人数」；人数不足时缩小规模而不是降低标准。
5. **双向确认**：`create_room` 必须经过 `pending_confirmation`，后端未确认直接 409——可以当场用 API 文档演示。
6. **官方 API 与模型都可替换**：`TMEDataProvider` 抽象 + `official_tme.py` 的 TODO 清单，入围后替换数据源不用改 Agent。

## 常见提问

| 提问 | 回答 |
| --- | --- |
| 数据是真实的吗？ | 全部为**脱敏 Demo 数据**，演出、用户、歌曲均为虚构，页面与接口都有标注。 |
| 接入 QQ 音乐了吗？ | 没有。初赛未提供 TME 官方 API，已预留 `official_tme.py` 适配接口与替换步骤。 |
| 匹配为什么可信？ | 四维加权（音乐 40 / 期待 25 / 社交 20 / 交流安全 15）+ 六条硬条件，返回 `score_breakdown` 与带来源的 `evidence`，理由做引用校验。 |
| 大模型失败怎么办？ | 自动回退到本地规则解析与文案模板，主链路照常跑完（案例 3）。 |
| 精确位置 / 支付 / 聊天呢？ | 明确不做。只给**公开集合建议**，不共享精确位置、不涉及转账。 |
| 真的会创建房间吗？ | 会，但必须**双方确认**；未确认时后端返回 409，前端也不会显示房间入口。 |
